# 판단만 하는 모델

[시리즈 색인](00-시리즈-색인.md) · 앞 편은 [불균형 지표가 뜻하지 않는 것](03-불균형-지표.md)입니다.

여기서부터 네 편은 Jev 이야기입니다. TypeSafe AI가 2026년 9월에 낸 모델인데,
글을 만들지 않습니다.

## 예시 하나로 시작하겠습니다

기존 언어 모델에게 "미국이 한국보다 커?"라고 물으면 면적과 인구와 역사를 늘어놓다가 결론에
닿습니다. Jev에게 같은 것을 물으면 이렇게 나옵니다.

```
0.98
```

끝입니다. 답만 있으면 되는 자리에서 언어 모델은 필요 없는 생성을 한다는 것이 이 모델의
출발점입니다.

## 왜 그게 문제였나

언어 모델을 **이해하는 쪽**과 **만들어 내는 쪽**으로 나눠 보면, 지금까지의 발전은 만들어
내는 쪽을 고도화하는 방향이었습니다. 긴 추론, 사고 사슬, 도구 사용이 다 그쪽입니다.

그런데 소프트웨어가 실제로 필요한 것은 결정일 때가 많습니다. 이 요청을 사람에게 올릴지,
이 버튼을 누를지, 이 사례가 중대한지 같은 것들인데 여기에 문장을 만들 이유가 없습니다.
그래서 Jev는 이해하는 쪽은 비슷하게 갖추되 출력을 숫자로 바로 내는데, 구조를 셋으로 줄이면
입력을 이해하는 인코더와 언어 생성이 없는 확률 출력, 그리고 확률이 왜곡되지 않게 잡아 주는
강화학습입니다.

이름이 System One인 이유는 카너먼이 나눈 두 가지 사고에서 따왔기 때문입니다. 빠르고 직관적인
판단이 System 1, 느리고 숙고하는 추론이 System 2입니다. 지금까지 언어 모델이 System 2를
흉내 냈다면 이쪽은 System 1 자리를 겨냥합니다.

## 세 가지 질문 형

상태(state) 하나를 주고 질문(questions)을 여러 개 얹습니다. 질문마다 형이 있습니다.

| 형 | 하는 일 | 돌려주는 것 |
|---|---|---|
| `noul` | 예아니오에 답한다 | 그 진술이 참일 확률 |
| `choice` | 주어진 선택지에서 고른다 | 선택지별 확률과 전체 신뢰도 |
| `score` | 낮음, 보통, 높음처럼 순서 있는 등급을 매긴다 | 연속 점수와 분포와 신뢰도 |

호출은 `POST api.typesafe.ai/v1/systemone` 하나입니다. LangChain 연동도 있습니다.

```python
from langchain_typesafe import Noul, TypeSafeClassifier

classifier = TypeSafeClassifier()
response = classifier.invoke({
    "state": "The deploy failed twice and customers are seeing 500s. Can someone look now?",
    "questions": {"urgent": Noul(instructions="Does this need attention right now?")},
})
urgency = response.nouls["urgent"].noul   # 0.999
```

여기서 구현에 걸리는 것이 하나 있습니다. 호출 형태가 `state`와 `questions`이고
`chat/completions`가 아닙니다. OpenAI 호환 규격을 전제로 만든 코드에 붙이려면 어댑터를
따로 둬야 합니다. 저희는 그 어댑터를 쓰고 있습니다.

## 값이 재미있게 매겨집니다

**입력 토큰에만 과금하고 출력은 무료**입니다. 글을 안 만드니 낼 것이 없기 때문입니다.
입력은 백만 토큰당 0.042달러입니다.

그런데 저희 측정에서 입력 토큰이 오히려 많았습니다. 같은 판단에 Jev가 929토큰,
Nemotron이 309토큰입니다. 질문 정의가 전부 입력에 들어가기 때문입니다. 비용 이점은 토큰
수를 줄여서가 아니라 **단가가 낮고 출력이 0이라서** 나옵니다. 이 구분을 해 두면 나중에
비용을 추정할 때 틀리지 않습니다.

## 속도는 실제로 빠릅니다

저희가 직접 잰 값으로는, 7문항을 한 호출에 넣어 답을 받는 데 **296밀리초**이고 같은 문항을
글을 생성하는 방식으로 풀면 **2,286밀리초**여서 약 7.7배입니다.

공급사는 40배에서 200배를 주장하고 워크플로 평가에서 193.6배 빠르고 444.6배 저렴하다고
밝혔습니다. 차이가 큰데 저희 수치를 씁니다. 공급사 값은 자체 측정이고 독립 재현이 아직
없기 때문입니다.

## 공급사가 스스로 밝힌 한계

이쪽이 더 중요합니다.

- 글을 못 만듭니다. 문자열 생성을 포기한 설계입니다. 언어 모델을 그대로 대체하지 못합니다
- 이미지를 못 받습니다. 구조화된 상태만 받습니다
- 선택지는 255개까지입니다. 그보다 많으면 두 단계로 나눠 점수를 매겨야 합니다
- 환각 0퍼센트는 실측이 아닙니다. 스키마가 맞는다는 보장이지 답이 옳다는 뜻이 아닙니다

평가 방법론의 한계도 공급사가 적어 두었습니다. 평가에 쓴 워크플로를 자사 팀이 직접 만들었고,
경쟁 모델을 자사 어댑터로 돌렸습니다. 환각 비교로 든 45.5퍼센트는 한 모델에서 나온 값이고
대부분의 모델은 0.58에서 13.2퍼센트 사이에 있습니다.

## 저희가 특히 새긴 한 가지

보정은 집단의 성질이고 개별 답의 보장이 아니라는 점을 공급사도 분명히 적어 두었습니다.
확률이 0.98이라는 것은 그런 답을 여럿 모았을 때 98퍼센트가 맞더라는 뜻이지, 지금 이 한 건이
맞다는 뜻이 아닙니다.

이 프로젝트가 걸러내는 과잉해석이 정확히 이런 종류입니다. **Jev를 쓰면서 개별 확률을 확신으로
읽으면 우리가 만든 규칙을 우리가 어기게 됩니다.** 그래서 화면과 출력에 확률을 그대로 보여
주되, 그 확률로 자동 종결하는 경로는 두지 않았습니다. 사람이 판정하고 사람이 제출합니다.

그리고 저희 측정에서 보정이 실제로 안 맞습니다. ECE 0.128이고 0.4에서 0.6 구간에서는 예측
0.485에 실제 0.702여서, 임계값을 그대로 쓰면 중대 사례를 놓칩니다. 운영에 쓰려면 구간
보정이 먼저입니다.

## 어디에 쓸 만한가

건수가 많고 빠른 판단이 중요한 자리입니다. 화합물 하나를 깊게 따라가는 일에서는 이점이
드러나지 않고, **FAERS 보고가 쏟아질 때 어느 것을 사람이 먼저 봐야 하는지 가르는 일** 같은
쪽에서 드러납니다. 역할을 나누면 오래 남을 기준과 규정은 큰 모델이 정하고 건건이 즉시
내려야 하는 판단은 Jev가 맡는 모양이 됩니다.

프롬프트를 쓰는 일이 아니라 스키마를 짜는 일입니다.
