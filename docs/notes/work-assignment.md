## 먼저 정직하게: 왜 나누는가

**팀장이 혼자 해도 대부분 끝낼 수 있다.** 아래 일 가운데 팀장이 못 하는 것은 거의 없다.
그러니 "일손이 모자라서" 나누는 것이 아니다. 나누는 이유가 셋이고, 그 셋에 해당하지 않는 일은
굳이 넘기지 않는다.

**1. 대신 할 수 없는 것이 있다.**

- **구글 폼.** 다섯 명이 각자 내야 하고 9/27 까지다. 팀장이 대신 낼 수 없다
- **DLI 수료.** 전원 수료로 가정하고 있으므로 각자 들어야 한다
- **FDDD.** 팀원 A 의 저작물이다. 쓰려면 본인 승낙과 라이선스 확인이 필요하다

**2. 검증은 만든 사람이 하면 안 된다.**

이것이 가장 중요한 이유다. **이 프로젝트의 주장 자체가 "작성자와 검증자를 나눠야 한다" 이다.**
크리틱을 작성자와 분리한 것도, 검수 에이전트를 따로 둔 것도 같은 규율이다.

그런데 규칙 15종을 팀장이 쓰고 케이스도 팀장이 만들고 그 타당성도 팀장이 판정하면 순환이다.
`docs/notes/paper-plan.md` 의 정직한 한계 절에 이미 적어 두었다.
"규칙을 만든 사람이 케이스도 만들면 순환이다. 규칙 작성자와 케이스 작성자를 갈라야 한다."

**약사가 라벨 판정을 확인하고 신약개발 전문가가 도킹 규칙을 확인하는 것은 일손 문제가 아니라
독립성 문제다.** 심사위원이 "이 규칙이 맞다고 누가 확인했나" 를 물으면 답이 달라진다.

**3. 팀장이 임계 경로에 있다.**

저장소와 설정과 영상과 신청서와 제출이 전부 팀장 손에 있다. 그것만으로도 3일이 빠듯하다.

### 그래서 정한 원칙

**임계 경로가 아닌 일만 넘긴다.** 누가 못 해도 제출은 된다.
그리고 **한 사람에게 하나씩만** 준다. 3일에 여러 개를 주면 아무것도 안 온다.

### A-2. `flybrain_pose` 도구 (선택)

**먼저 알아야 할 것.** 초파리 경로는 **근거가 아니라 대조 대상**이다. 규칙 9번이
"초파리 포즈 탐색 성공을 효능이나 약효의 근거로 말하면 반려" 다. 그러니 이 도구가 결론을
바꾸지 않는다. 세 번째 경로를 나란히 보여 주는 것이 목적이다.

세 가지 중에 고른다. **위로 갈수록 안전하고 아래로 갈수록 값어치가 크다.**

| 안 | 내용 | 드는 시간 | 위험 |
|---|---|---|---|
| **1. 조회 도구** | 팀원 A 가 FDDD 에서 돌린 결과를 JSON 으로 내려 두고, 우리 도구가 그것을 읽는다 | 한두 시간 | 낮음 |
| **2. Node 헤드리스 실행** | FDDD 엔진을 Node 에서 직접 돌린다 | 서너 시간 | 중간 |
| 3. 화면 녹화 | 데모를 녹화해 영상에만 넣고 도구는 만들지 않는다 | 30분 | 없음 |

**2안이 가능한 것은 확인했다.** 엔진이 의존성 없는 ES 모듈 셋이고 전부 200 으로 받아진다.

```
https://drug.flybrain.kr/engine/malecns/core.js          LIF 엔진. initEngine, resetEngine, stepEngine
https://drug.flybrain.kr/engine/malecns/worker.js         메시지 배선
https://drug.flybrain.kr/engine/malecns/spike-codec.js    스파이크 압축
https://drug.flybrain.kr/engine/malecns/LICENSE-MIT.txt   상류 MIT (Seth Miller, 2017)
```

`initEngine(buffer, rootIds, manifest, {feedingIndices, seed})` 로 커넥톰을 싣고
`stepEngine(sensory, mode)` 를 틱마다 부른다. **`sensory[8]` 이 보상 채널이고 여기에 도킹 점수를
정규화해 넣는다.** 미각 뉴런 1,428개가 그것을 받는다. 자세한 분해는 `docs/notes/fddd-teardown.md`.

커넥톰이 27.4 MB 라 저장소에 넣지 않는다. 받아서 캐시하고 출처만 밝힌다.

어느 안이든 **도구가 돌려줄 것**은 같다.

- 실행 파라미터: seed, 틱 수, 보상 채널에 넣은 값과 그 정규화 방식
- 결과: 미각과 운동 뉴런 집단의 스파이크 수, 운동 출력 3값
- 대조군: `baseline` 과 `silenced` 를 함께 돌린 값. **엔진에 이미 있다.** 대조가 있어야 신뢰가 선다
- 근거 ID `fly:run:<해시>`
- **해석 한계 문장.** 이 값은 효능이나 결합 세기의 근거가 아니다

### A-2b. 도메인 설명 1~2분 녹화 (여유가 되면, 값어치가 크다)

**주최 측 허가를 기다리지 않는다.** 9/28 제출 영상은 우리 산출물이라 마음대로 넣을 수 있다.

제출 영상이 2~3분이고 구간 배분에 계보 20초와 안전 25초가 잡혀 있다. 그 자리에 **도메인
전문가가 직접 말하는 20~30초**가 들어가면 무게가 완전히 달라진다.

말할 것은 하나면 된다. **"도킹 점수로 말할 수 있는 것과 없는 것의 경계가 실제로 어디인가,
그리고 왜 그 경계를 넘는 요약이 현업에서 문제가 되는가."** 검토하면서 느낀 것을 그대로 말하면 된다.

- 휴대폰 카메라로 충분하다. 편집하지 않아도 된다
- 배경과 조명을 신경 쓰지 않아도 된다. 내용이 전부다
- 한 번에 안 되면 여러 번 찍어 보내 주면 우리가 고른다
- 잘 나오면 10/7 본선과 11/10 무대에 그대로 재사용한다

**검토 의견이 먼저다.** 둘 중 하나만 된다면 글로 된 검토를 받는다.

### C-1. `jev_triage` 도구 (필수 아님, 그러나 이 사람이 적임)

남은 미구현 도구 둘 중 하나다. 자기완결적이고 다른 작업을 막지 않는다.

**중요한 제약.** Jev 는 채팅 모델이 아니라 `evaluation` 형이다. 공유 상태와 타입 있는 질문을

- 접근은 Vercel AI Gateway 의 `typesafe-ai/jev`. 입력 백만 토큰당 0.042달러, 출력 0달러.
  **Vercel 계정과 결제 수단이 필요하다.** 없으면 팀장에게 알린다
- 하는 일은 후보를 `screen`, `skip`, `review` 로 나누는 것이다. `review` 만 Nemotron super 로 넘긴다
- **측정이 핵심이다.** 아낀 DiffDock 호출 수, 두 경로의 지연, 판정 일치율, 그리고
  **Jev 를 뺀 ablation 에서 파이프라인이 그대로 도는지.** 숫자가 없으면 넣은 이유를 댈 수 없다
- 못 쓰게 되면 `nemotron-3.5-lightning` 으로 같은 구조를 만든다. 계획이 무너지지 않는다

등록 절차는 `.claude/skills/nat-tool-add/SKILL.md` 를 그대로 따른다.

### D-1. 적발률 재측정 (필수, 짧고 값어치가 크다)

발표에 쓸 헤드라인 숫자를 확정하는 일이다.

지난 측정에서 NVIDIA 쪽 503 으로 1건이 판정을 못 받아 평균이 0.9697 에 머물렀다.
**판정 실패 0건인 실행을 한 번 만들면 상한이 1.0 이다.**

```bash
set -a; source .env; set +a
.venv/bin/nat eval --config_file configs/eval.yml
CRITIC_DETERMINISTIC_ONLY=true .venv/bin/nat eval --config_file configs/eval.yml
```

**두 수치를 함께 기록한다.** 차이가 LLM 의미 판단의 몫이다. 503 이나 429 가 섞이면 다시 돌린다.
`max_concurrency: 1` 이 이미 설정돼 있다. 절차는 `.claude/skills/evidence-gate/SKILL.md` T5.

**저장소를 공개로 돌리므로 팀원 실명을 쓰지 않는다.**

### D-3. 에이전트 관점 검토 (선택, 시간이 남으면)

## 팀장

하네스 배선, 영상 원고와 렌더, 신청서 문안, 제출 PDF, 그리고 조율이다.
저장소를 쥐고 있으므로 충돌이 날 파일은 팀장이 합친다.

## 파일 충돌을 막는 규칙

여럿이 동시에 고치면 충돌한다. **담당 경로를 나눠 쓴다.**

| 사람 | 고쳐도 되는 곳 |
|---|---|
| 팀원 A | `src/harness/tools/flybrain_pose.py`(신규), `docs/notes/credits.md` |
| 팀원 B | `eval/results/case_*.json`(새 케이스), 검토 의견은 `docs/notes/review-*.md` 새 파일로 |
| 팀원 C | `src/harness/tools/jev_triage.py`(신규), `tests/test_jev_triage.py` |
| 팀원 D | `README.md`, `eval/results/critic_verdict_output*.json` |
| 팀장 | `configs/`, `src/harness/register.py`, `docs/HANDOFF.md`, `assets/` |

**`configs/` 와 `register.py` 는 팀장만 고친다.** 도구를 새로 만들면 모듈까지만 하고
배선은 팀장에게 넘긴다. 그래야 두 설정 파일이 어긋나지 않는다.

커밋은 각자 본인 GitHub 신원으로 한다. **AI 도구를 공동저자로 적지 않는다.**
