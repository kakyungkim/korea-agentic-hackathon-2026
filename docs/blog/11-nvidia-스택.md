# NVIDIA 에이전트 스택 실전

[시리즈 색인](00-시리즈-색인.md) · 앞 편은 [비유인가 기여인가](10-커넥톰-대조.md)입니다.

여기까지가 판단 로직이었습니다. 이 편은 그것을 **에이전트로 포장하고 가둬 두는** 쪽입니다.
모델을 고르고, 도구로 등록하고, 출력 형식을 맞추고, 가드를 걸고, 샌드박스에 넣는 순서로
갑니다. 문서에 적힌 대로 되지 않은 곳이 여러 번 있었고 그때마다 직접 재서 적었습니다.
날짜를 함께 적어 둔 것은 **이 바닥의 수치가 몇 주 만에 바뀌기 때문**입니다.

## NIM이 무엇이고 주소가 왜 셋인가

NIM은 NVIDIA Inference Microservice의 약자입니다. 모델 하나를 컨테이너에 담아 HTTP로
부르게 만든 것이고, 채팅 모델 쪽은 **OpenAI 호환 규격**을 그대로 씁니다. OpenAI SDK의
base_url만 바꾸면 그대로 돕니다. 직접 띄울 수도 있지만 우리는 NVIDIA가 호스팅하는 쪽을
썼습니다.

여기서 처음 걸립니다. **주소가 하나가 아닙니다.**

| 주소 | 무엇이 있나 | 우리가 쓴 것 |
|---|---|---|
| `integrate.api.nvidia.com/v1` | 채팅, 임베딩. OpenAI 호환 | Nemotron 계열 전부 |
| `health.api.nvidia.com/v1/biology` | 생물학 모델(BioNeMo) | MSA-Search, OpenFold3, DiffDock, Boltz-2 |
| `ai.api.nvidia.com/v1/retrieval` | 검색과 재정렬 | 리랭커 |

세 곳은 **키는 같은데 목록이 서로 다릅니다.** 이걸 모르면 아래 같은 사고가 납니다.

### 목록에 없다고 없는 것이 아닙니다

9월 24일에 `integrate.api.nvidia.com/v1/models`를 호출해 82개를 받았습니다. 그 안에
rerank 계열이 하나도 없었습니다. 그래서 저희는 이렇게 적었습니다.

> NeMo Retriever 리랭커는 없다. 이 계정의 모델 목록 82개에 rerank 계열이 하나도 없어
> 신청서 기술 스택에서 리랭커를 빼야 한다.

**틀렸습니다.** 리랭커는 `integrate`가 아니라 `ai.api.nvidia.com`의 retrieval 경로에
있었습니다. 나흘 뒤인 9월 28일에 실제로 불러 성능까지 쟀습니다(아래 "리랭커가 실제로
올려 준 것" 절). 한 엔드포인트의 목록을 전수 조사로 착각한 것입니다.

**교훈이 분명합니다. "목록에 없다"는 "그 호스트에 없다"는 뜻입니다.** 모델 종류가 다르면
호스트가 다를 수 있습니다. 없다고 결론 내리기 전에 그 기능의 공식 문서에서 **엔드포인트
주소를 먼저 확인**하세요.

반대쪽 함정도 있습니다. 목록에 올라와 있는데 부르면 안 되는 모델이 있습니다. 쓸 모델을
전부 최소 호출로 직접 확인했습니다. 아래는 2026-09-24에 저희 키로 실제 요청을 보내 받은
응답입니다.

| `nvidia/nemotron-3.5-lightning-30b-a3b` | OK | 가벼운 작업 |
| `nvidia/nemotron-3-ultra-550b-a55b` | OK | |

**저희 계획서에 적어 둔 모델 ID 두 개가 둘 다 죽어 있었습니다.** 하나는 9월 1일에 종료됐고
하나는 목록에만 남아 있었습니다. 계획서를 쓴 시점과 구현을 시작한 시점 사이에 바뀐 것입니다.

목록 개수도 움직입니다. 9월 24일에 82개였고 10월 5일에 다시 재니 81개였습니다.

이래서 **폴백 사슬**을 깔았습니다. 주 모델이 응답하지 않으면 다음으로 넘어갑니다.

```
nemotron-3-super-120b-a12b  →  nemotron-3-ultra-550b-a55b  →  nemotron-3.5-lightning-30b-a3b
```

대회 당일처럼 여러 팀이 같은 API를 두드리는 상황에서는 이게 보험이 아니라 필수입니다.

## 구조화 출력은 response_format으로 받으세요

에이전트는 JSON을 받아야 다음 단계로 넘길 수 있습니다. LangChain에는
`with_structured_output()`이 있는데 **Nemotron 3 엔드포인트에서는 쓰지 않는 편이 낫습니다.**

`ChatNVIDIA`는 구조화 출력을 세 형식으로 차례로 시도합니다. 앞 형식이 실패하면
`nvext.guided_json`으로 넘어가는데 Nemotron 3이 그 필드를 거부합니다.

```
400 unknown field `guided_json`, expected one of `greed_sampling`, `use_raw_prompt`, ...
```

**여기가 고약합니다.** 폴백이 마지막 예외만 올리는 구조라, 앞 단계에서 무슨 일이 났든
화면에는 이 `guided_json` 오류만 보입니다. 진짜 원인을 가립니다.

같은 프롬프트로 네 가지를 재 봤습니다.

| 방법 | 결과 |
|---|---|
| `response_format: {"type": "json_schema", ...}` | **OK.** 스키마에 맞는 JSON만 돌아옵니다 |
| `response_format: {"type": "json_object"}` | OK. 스키마를 강제하지 않아 필드가 제멋대로입니다 |
| 프롬프트로만 JSON 요청 | OK. 모델이 필드를 지어냅니다 |
| `nvext: {"guided_json": ...}` | 400 거부 |

그래서 `llm.bind(response_format=...)`으로 OpenAI 호환 json_schema를 직접 싣습니다.
스키마는 pydantic 모델의 `model_json_schema()`에서 만듭니다.

받은 응답도 그냥 믿지 않습니다. `</think>` 뒤만 남기고, 중괄호 균형을 세어 최상위 JSON
객체를 모은 뒤 원하는 키를 가진 것을 고릅니다. 마크다운 펜스와 앞뒤 서술, 한 겹 더 감싼
응답까지 걷어냅니다. 그래도 형식이 어긋나면 "JSON만 출력하라"를 붙여 한 번 더 요청하고,
끝내 안 되면 **예외를 삼키지 않고 판정을 `needs_human`으로 둡니다.**

## Agent Skills: 382개 중에서 고르기

NVIDIA가 공개한 스킬 카탈로그에 폴더가 **382개** 있습니다. 스킬은 파이썬 패키지가 아니고
실행 파일도 아닙니다. **에이전트가 읽는 사용 설명서 묶음**입니다.

```
skills/<스킬명>/
  SKILL.md         앞머리(YAML)에 이름, 용도, 라이선스, 허용 도구. 본문에 절차와 예제
  references/*.md  조건부로 읽는 상세 문서 (api, parameters, science, validation 등)
  skill-card.md    거버넌스용 요약 카드
  BENCHMARK.md     그 스킬로 에이전트를 돌린 벤치마크 기록
```

설치는 한 줄입니다. 설치하면 에이전트가 그 문서를 읽고 규격에 맞게 호출합니다.

```bash
npx skills add NVIDIA/skills --skill bionemo-openfold2-nim
```

카탈로그가 크니 다 보면 안 됩니다. 필요한 것을 이름으로 찾는 쪽이 빠릅니다. 실제로 쓴
것만 적으면 넷입니다.

| 스킬 | 어디에 |
|---|---|
| `diffdock-nim` | 도킹 호출 규격. **과잉해석 규칙 하나의 출처가 이 문서** |
| `bionemo-msa-structure-prediction-pipeline` | MSA에서 구조까지 이어 붙이는 순서 |
| `bionemo-openfold2-nim` | 구조 예측 규칙 2종의 출처 |
| `nemotron-policy-generator` | 안전 정책 생성 |

스킬 문서를 규칙의 출처로 쓴 것이 여기서 배운 방식입니다. 스킬에는 도구 사용법만 적혀
있는 것이 아니고 **하면 안 되는 것도 적혀** 있습니다. 그 문장을 크리틱 규칙으로 옮기면
취향 다툼이 되지 않습니다. [8편](06-근거-id-크리틱.md)과 [10편](08-bionemo-네-단계.md)에서
본 것이 이것입니다.

우리 기능도 같은 규격으로 포장했습니다. 제출 시점에 열한 개였고 지금 저장소에는 `SKILL.md`가
열여섯 개 있습니다(2026-10-05 기준). 트리아지, 근거 등급, 문헌 읽기, 크리틱, 창고 조회
같은 것들입니다. 같은 규격으로 쓰면 다른 에이전트가 우리 것을 가져다 씁니다.

## 도구로 등록해야 에이전트가 부릅니다

모델과 스킬이 있어도 에이전트가 **부를 수 있는 형태**가 아니면 소용이 없습니다. NeMo Agent
Toolkit에서는 함수에 데코레이터를 붙여 등록합니다.

```python
from nat.cli.register_workflow import register_function
from nat.data_models.function import FunctionBaseConfig

class EchoToolConfig(FunctionBaseConfig, name="echo_tool"):   # name 이 YAML 의 _type
    prefix: str = ""

@register_function(config_type=EchoToolConfig)
async def echo_tool(config: EchoToolConfig, builder: Builder):
    async def _echo(text: str) -> str: ...
    yield FunctionInfo.from_fn(_echo, description="...", converters=[...])
```

`name`에 적은 것이 설정 파일 YAML의 `_type`이 되고, 그 이름을 워크플로의 `tool_names`에
실어야 에이전트가 봅니다. 저희는 이렇게 여덟 개를 실었습니다. FAERS 조회, 라벨 검색,
문헌 조회, 불균형 지표 계산, 도킹, 참조 결합값, 구조 참조, 에코입니다.

**여기서 한 번 크게 틀렸습니다.** 도구 셋이 공개 API로 멀쩡히 동작하는데 에이전트는 그걸
부를 수 없는 상태로 한동안 가 있었습니다. 등록 코드가 주석 처리돼 있었고 `tool_names`에도
없었습니다. 심사 첫 항목이 "NVIDIA Agent 기술 활용 심도"였으니 가장 큰 구멍이었습니다.
**도구가 돈다와 에이전트가 그 도구를 부른다는 다릅니다.**

### `nat validate`가 통과해도 `nat run`에서 죽습니다

설정 검증은 통과하는데 실행에서 막힌 일이 둘 있었습니다. 둘 다 가드레일 미들웨어 쪽입니다.

1. `LLM 'planner' not found`. 미들웨어의 모델 바인딩이 평범한 문자열 맵이라 의존 그래프에
   잡히지 않고, **미들웨어가 모델보다 먼저 만들어집니다.** 참조형 필드에 모델을 함께 적어
   순서를 잡았습니다
2. `llm_bindings['planner'] must resolve to a LangChain BaseLanguageModel; got
   RunnableConfigurableFields`. 툴킷이 모델을 한 겹 감싸는데 NeMo Guardrails는 맨 모델을
   요구합니다. 우회할 설정이 없어 바인딩을 빼고 레일이 자기 설정으로 모델을 만들게 뒀습니다

**검증은 형식을 보고 실행은 순서를 봅니다.** 검증 통과를 동작 확인으로 쓰면 안 됩니다.

## 범용 안전 가드는 도메인 과잉해석을 못 잡습니다

이 절이 이 편에서 가장 쓸모 있는 부분이라고 생각합니다.

약물감시에서 가장 위험한 문장은 욕설이나 혐오 표현이 아닙니다. **"PRR 94.173은 인과관계를
증명한다"** 같은 문장입니다. 보고 건수의 불균형을 인과로 바꿔 읽는 것이고, 겉보기에는
멀쩡한 전문 문장입니다.

네 가지 구성을 같은 입력에 걸어 재 봤습니다. 평가 50건입니다.

| 구성 | 정확도 | 지연 중앙값 |
|---|---|---|
| Safety Guard 8B v3 (기본 분류) | **0.58** | 691.6 ms |
| 3.5 Content Safety (기본 분류) | 0.72 | 356.2 ms |
| 3.5 Content Safety + **약물감시 정책** | **0.84** | 459.2 ms |
| 위에 숙고 모드까지 | 0.898 | **4292.4 ms** |

PRR을 인과로 단정하는 문장 7건만 떼어 보면 차이가 더 분명합니다.

| 구성 | 7건 중 적발 |
|---|---|
| Safety Guard 8B v3 (기본 분류) | **0** |
| 3.5 Content Safety (기본 분류) | 2 |
| 3.5 Content Safety + 약물감시 정책 | **7** |

**기본 분류 체계로는 하나도 못 잡습니다.** 모델이 나빠서가 아니라 그 분류 체계에 "통계적
연관을 인과로 단정하기"라는 항목이 없기 때문입니다. 범용 가드는 범용 위험을 봅니다.

그래서 정책을 써서 넣었습니다. 공식 스킬 `nemotron-policy-generator`로 만들어
`custom_policy`로 넘겼습니다. 금지 항목은 다섯입니다. 개별 치료 조언, PRR을 인과로 읽는
단정, 자발 보고로 발생률을 내는 것, 재식별 시도, 허용 외 도구 사용입니다.

숙고 모드는 정확도를 0.84에서 0.898로 올리는 대신 **지연이 9배가 됩니다.** 저희는 쓰지
않았습니다. 가드는 모든 주장마다 도는 층이라 지연이 그대로 전체 지연이 됩니다.

**되지 않은 것도 적어 둡니다.** NemoGuard 판정 모델로 차단을 시연하려 했으나 호스팅 쪽이
500과 타임아웃을 돌려줘 끝내 보여 주지 못했습니다. 배선은 맞고 모델이 죽어 있었습니다.

## 리랭커가 실제로 올려 준 것

문헌을 읽을 때 PubMed가 주는 순서를 그대로 쓰면 위쪽에 관련 없는 논문이 섞입니다. 저희는
후보 20편을 받아 **다시 줄 세운 뒤 위에서 6편만 읽습니다.**

2026-09-28에 쌍 30건, 논문 575편으로 쟀습니다. 위 6편 안에 관련 문헌이 들어온 비율입니다.

| 방법 | 상위 6편 정확도 | AUC |
|---|---|---|
| PubMed 기본 순서 | 0.650 | 0.429 |
| 제목 규칙으로 거르기 | 0.767 | 0.652 |
| **Nemotron 리랭커** | **0.850** | 0.778 |
| Nemotron 임베딩만 | 0.850 | 0.781 |

**리랭커가 0.65를 0.85로 올렸습니다.** 읽는 6편 중 한 편꼴로 섞이던 무관한 논문이 줄었다는
뜻입니다. 호출 지연은 중앙값 430밀리초이고 한 번에 20편을 넘깁니다.

정직하게 둘을 덧붙입니다. 첫째 **임베딩만 써도 같은 0.85가 나왔습니다.** 리랭커가 상위 3편
기준과 AUC에서 조금 앞서지만 이 표본에서 둘의 차이는 크지 않습니다. 둘째 질의 문구를 셋으로
바꿔 보니 **문구 사이 차이가 최대 0.022**였습니다. 질의를 다듬는 것보다 재정렬 단계를 넣는
것 자체가 훨씬 큰 차이를 만들었습니다.

## CLI 하나로 사람과 에이전트가 같은 명령을 씁니다

`flygate` CLI입니다. 설치는 한 줄입니다.

./scripts/install_flygate.sh
```

```

전부 근거 ID가 붙은 JSON을 냅니다. 화면에 보기 좋은 표를 내는 것이 아니고 기계가 받을 수
있는 형태를 냅니다. 사람이 볼 표는 그 JSON에서 만듭니다.

이 설계가 왜 좋은가 하면, **에이전트와 사람이 같은 도구를 쓰기 때문**입니다. 에이전트가 하는
일을 사람이 그대로 재현할 수 있고, 사람이 의심스러우면 같은 명령을 직접 쳐 볼 수 있습니다.
에이전트 전용 경로를 따로 두면 그 경로에서 일어난 일을 사람이 확인하기 어렵습니다.

인자 없이 `flygate`만 치면 대화형 모드가 열립니다. 자연어 요청을 받아 **실행할 명령을 제안한
뒤 확인을 받고** 돌립니다. 바로 실행하지 않는 것이 중요합니다. 자연어 해석이 틀릴 수 있고,
틀린 명령이 실행되기 전에 사람이 봅니다.

## 국내 보고 서식도 같은 방식으로 다룹니다

명령 아홉 개 가운데 `kr-causality` 는 국내용입니다. 미국 FAERS 와 한국 보고 체계는 서식과
인과성 평가 방식이 다른데, 같은 사례를 국내 서식의 칸에 맞춰 구조화하는 일을 Nemotron 3
Super 의 JSON 모드로 합니다.

여기서 지킨 것이 둘입니다. 첫째 **모델에게 판정을 시키지 않고 칸을 채우게** 합니다. 인과성
등급 자체는 WHO-UMC 나 Naranjo 같은 정해진 체계가 내고, 모델은 서술에서 각 항목에 해당하는
내용을 뽑아 배치합니다. 둘째 **뽑은 항목마다 원문 어디에서 왔는지 근거 ID 를 붙입니다.**
서식을 채우는 일은 요약이 아니라 대응이라, 어느 문장에서 왔는지 따라갈 수 있어야 검토자가
씁니다.

규정이 정하는 기한도 나라마다 다릅니다. 그 대응은 [5편](05-jev-누수와-경로-설계.md)의
경로 설계에 적었습니다.

## OpenShell 샌드박스: 나가는 길을 먼저 막습니다

NemoClaw 배포 구성 안에서 OpenClaw 에이전트가 같은 CLI를 씁니다. 정책은
`agent/policy/flygate.yaml`입니다.

원칙이 하나입니다. 나가는 연결을 기본으로 모두 막고 목록에 적은 호스트만 엽니다.
차단 목록을 만드는 방식이 아니고 허용 목록을 만드는 방식입니다. 차단 목록은 빠뜨리면
열리고, 허용 목록은 빠뜨리면 막힙니다. 틀렸을 때 안전한 쪽으로 틀립니다.

파일 접근은 Landlock으로 제한합니다. 커널 수준에서 막으므로 프로세스가 우회할 수 없습니다.
루트 권한 없이 돕니다.

보고서를 밖으로 보내는 경로는 아예 열지 않았습니다. 사람이 판정하고 사람이 제출한다는
뜻입니다. 에이전트가 규제기관에 무언가를 보낼 수 있으면 그건 다른 종류의 시스템입니다.

## 정책이 실제로 강제되는지 확인했습니다

정책 파일을 쓰는 것과 그 정책이 강제되는 것은 다릅니다. 스모크 테스트를 돌려
`pass=9 fail=0`을 받았습니다.

| 구분 | 대상 | 결과 |
|---|---|---|
| 허용 | `api.fda.gov` | `http=200` |
| 허용 | `dailymed.nlm.nih.gov` | `http=200` |
| 허용 | `eutils.ncbi.nlm.nih.gov` | `http=200` |
| 허용 | `integrate.api.nvidia.com` | `http=200` |
| **차단** | `example.com` | `CONNECT tunnel failed, response 403` |
| **차단** | `github.com` | `CONNECT tunnel failed, response 403` |
| 쓰기 거부 | `/etc` | `Permission denied` |
| 쓰기 허용 | `/work/out` | 쓰고 읽고 삭제까지 성공 |
| 쓰기 거부 | `/sandbox` | `Permission denied` |

`integrate.api.nvidia.com`이 401이 아니라 200을 돌려준 것이 중요합니다. 프록시가 진짜
키를 끼워 넣었다는 뜻입니다.

샌드박스 안에서 `printenv NVIDIA_API_KEY`를 하면 값이 아니라 자리표시자가 나옵니다.

```
openshell:resolve:env:v3_NVIDIA_API_KEY
```

에이전트가 키를 볼 수 없는데 호출은 됩니다. 프록시가 나가는 요청에 진짜 키를 끼웁니다.
에이전트가 키를 어딘가에 적어 보내는 사고를 구조로 막습니다.

## 로그를 읽을 때 걸린 것

네트워크 거부는 게이트웨이 로그에 남습니다.

```
NET:OPEN [MED] DENIED /usr/bin/curl(189) -> example.com:443
  [reason:endpoint example.com:443 is not allowed by any policy]
```

그런데 파일시스템 거부는 DENIED로 남지 않습니다. Landlock이 커널에서 EPERM으로 끊기
때문에 게이트웨이가 볼 이벤트가 없습니다.

이걸 모르면 "파일 정책이 안 걸렸다"고 오해합니다. 대신 적용 기록이 남습니다.

```
Applying Landlock filesystem sandbox [abi:V2 compat:BestEffort ro:12 rw:3]
Landlock ruleset built [rules_applied:14 skipped:1]
```

`skipped:1`은 이미지에 없는 경로 하나입니다. 읽기 전용 목록에 적었는데 이미지에 만들지
않았습니다. 호환 모드가 `best_effort`라 건너뛰고 넘어갑니다.

**`skipped`가 0인지 확인하세요.** 넘어간 규칙이 있는데 넘어갔다는 것을 모르면 정책이 적용된
줄 알게 됩니다. 반드시 걸려야 하는 경로면 `hard_requirement`로 바꿉니다.

## 이 편에서 가져갈 것

**모델과 주소**

- **주소가 셋입니다.** 채팅은 `integrate`, 생물학은 `health`, 검색은 `ai`. 한 곳의 목록을
  전수로 착각하지 마세요. 저희가 그래서 리랭커를 없다고 적었습니다
- **목록에 있어도 호출은 안 될 수 있습니다.** 쓸 모델은 최소 호출로 직접 확인하세요
- 계획서에 적은 모델 ID는 **구현 시작할 때 다시 확인**하세요. 저희는 둘 다 죽어 있었습니다
- **폴백 사슬을 깔아 두세요.** 대회처럼 호출이 몰리는 날에는 보험이 아니라 필수입니다

**출력과 등록**

- 구조화 출력은 `response_format`의 json_schema로 받으세요. 라이브러리 자동 폴백은
  **마지막 예외만 보여 줘 진짜 원인을 가립니다**
- 받은 JSON을 그냥 믿지 말고 걷어내는 층을 두고, 끝내 안 되면 **사람 확인으로 떨어뜨리세요**
- **도구가 도는 것과 에이전트가 그 도구를 부르는 것은 다릅니다.** 등록과 `tool_names`를
  확인하세요
- `validate` 통과는 동작 확인이 아닙니다. 검증은 형식을, 실행은 순서를 봅니다

**가드와 검색**

- **범용 안전 가드는 도메인 과잉해석을 못 잡습니다.** 기본 분류로 0/7이었고 정책을 넣어
  7/7이 됐습니다
- 가드의 숙고 모드는 정확도를 조금 올리고 **지연을 9배로** 만듭니다. 모든 주장마다 도는
  층이라는 것을 생각하세요
- 재정렬 단계 하나가 질의 문구를 다듬는 것보다 훨씬 큰 차이를 냅니다. 0.65에서 0.85입니다
- 다만 **임베딩만으로 같은 값이 나오기도 합니다.** 둘 다 재 보고 고르세요

**샌드박스**

- 카탈로그가 크면 이름으로 찾으세요. 다 읽는 것은 시간 낭비입니다
- 도구 문서의 **금지 문장**을 규칙의 출처로 쓰세요
- **사람과 에이전트가 같은 CLI를 쓰게** 하세요. 확인이 쉬워집니다
- 자연어 요청은 **실행 전에 명령을 보여 주고 확인**받으세요
- 허용 목록으로 막으세요. 틀렸을 때 안전한 쪽으로 틀립니다
- 정책을 쓴 것과 강제되는 것은 다릅니다. 스모크 테스트로 확인하세요
- 로그에 안 남는 종류의 거부가 있습니다. `skipped` 개수를 보세요
- 키를 에이전트에게 주지 말고 **프록시가 끼우게** 하세요
