# 근거 ID와 3단 크리틱

[시리즈 색인](00-시리즈-색인.md) · 앞 편은 [경로를 늘려 사람 일을 줄이기](07-jev-경로-설계.md)입니다.

이 프로젝트의 중심입니다. 모델이 쓴 문장이 **그 문장이 기댄 자료를 넘어섰는지** 검사합니다.

## 문제부터 보겠습니다

모델이 이런 문장을 냈다고 하겠습니다.

> 니라파립과 혈소판감소증의 PRR은 38.24이며 이는 니라파립이 혈소판감소증을 일으킨다는
> 강력한 증거다.

숫자 38.24도 맞고 출처도 실재하는데 결론이 틀렸습니다. 불균형 지표는 보고의 두드러짐을
재고 인과를 재지 않으니까요. 그런데 형식 검사로는 이걸 못 잡습니다. JSON 스키마도 통과하고
인용도 붙어 있어서, **숫자와 출처는 맞는데 결론만 넘어선 경우**를 잡으려면 다른 장치가
필요합니다.

## 주장마다 근거 ID를 붙입니다

먼저 모든 주장에 출처 식별자를 강제합니다. 형식이 정해져 있습니다.

```
faers:case:<보고번호>
faers:2x2:<약>:<반응>@<분기>
label:<setid>#<절>
pubmed:<PMID>#<연구설계>
grade:<약>:<반응>@<분기>
```

분기와 절 번호까지 넣는 것이 요령입니다. `faers:2x2:NIRAPARIB:THROMBOCYTOPENIA@2026Q2`는
어느 분기의 어느 표에서 나온 숫자인지가 ID 안에 들어 있습니다. 데이터가 갱신되면 같은 질문에
다른 답이 나오는데, 분기가 없으면 그 차이를 추적할 수 없습니다.

라벨도 `label:abc123#5.10`처럼 절 번호까지 넣는데, 왜 그래야 하는지는
[다음 편](09-근거-등급.md)에서 실제로 틀린 이야기로 나옵니다.

## 검사는 세 단계입니다

`api/_fv/assess.py`에 있습니다.

| 단계 | 하는 일 | 모델 |
|---|---|---|
| T1 | 인용한 근거 ID가 실재하는지 | **안 씀** |
| T2 | 문장 속 숫자가 원본과 맞는지 (±1.1%) | **안 씀** |
| T3 | 근거가 허락하는 범위를 넘었는지 | 씀 |

**앞의 둘이 모델을 안 쓴다는 게 핵심입니다.**

T1은 문자열 대조라, `faers:case:12345678`을 인용했으면 그 보고번호가 창고에 있는지 조회하고
없으면 반려합니다. 지어낸 인용은 여기서 전부 걸립니다.

T2는 숫자 비교입니다. 문장에서 숫자를 뽑아 원본 쿼리 결과와 견주는데, 허용 오차 1.1퍼센트는
반올림 차이를 통과시키려고 둔 값입니다. PRR 38.24를 38.2로 적는 것은 통과하고 48.24로 적는
것은 반려입니다.

이 두 단계가 만들기도 제일 쉽고 값어치도 큽니다. 문자열 대조와 숫자 비교가 전부이고, 모델이
필요한 것은 마지막 하나인 "근거가 허락하는 범위를 넘었는가"뿐입니다.

## 3단 규칙을 직접 짓지 않았습니다

여기가 이 프로젝트에서 가장 중요한 설계 결정입니다. **규칙을 직접 짓지 않고 도구와 데이터
제공자가 문서에 적어 둔 금지 문장에서 옮겼습니다.**

예를 들어 NVIDIA의 DiffDock 문서에 이 문장이 있습니다.

> Do not convert confidence directly into binding affinity.

이 한 줄이 그대로 규칙이 되어서, 도킹 신뢰도를 결합 세기로 환산한 문장은 반려합니다.

이렇게 하는 이유는 **취향 다툼이 되지 않기 때문**입니다. "이 해석이 과하다"는 판단은
사람마다 다르지만 "이 도구를 만든 쪽이 하지 말라고 문서에 적었다"는 것은 사실이라,
심사자가 반박하려면 NVIDIA 문서를 반박해야 합니다.

## 규칙 17종과 그 출처

규칙마다 출처를 코드에 달아 두었습니다.

| 출처 | 어디서 |
|---|---|
| 도킹 데이터 제공자의 주의 8항목 | 도킹 서비스 응답에 들어 있는 `notes` 필드 |
| NVIDIA DiffDock 문서 | 스킬 문서의 검증 절 |
| 기존 약물감시 규율 | 불균형 지표를 인과로 말하지 않는다 |

규칙 이름을 몇 개만 보면 성격이 드러납니다.

- 교차 타깃 순위 금지
- 친화도 환산 금지
- DiffDock 재현성 주장 금지
- 라벨 기재와 인과 구분
- 근거 범위 준수

문헌 귀속도 따로 달았습니다. 특정 서비스의 문서 하나에만 기대면 그 서비스가 사라질 때
규칙도 같이 사라집니다. 그런데 그 주의 8항목은 도킹 분야에서 널리 알려진 한계를 다시 적은
것이고 같은 내용이 동료심사 문헌에 있습니다. 그래서 출처를 둘로 달아, 한쪽이 빠져도 규칙이
서게 했습니다. 17종 중 12종이 그렇게 섭니다.

뒷받침이 없으면 없다고 적었습니다. 강도를 매겨 보니 매우 강함 1, 강함 2, 중간 6, 약함 2,
없음 4였고, 없음 넷은 도구 문서 수준의 사실이라 문헌을 억지로 붙이지 않고 사유를 따로
적었습니다. 억지로 붙이지 않는 것이 오히려 규칙 목록의 신뢰를 지킵니다. 15종 전부에 논문을
하나씩 달아 두면 그럴듯해 보이지만, 확인해 보는 사람이 하나라도 어긋난 걸 찾으면 나머지도
의심받습니다.

## 규칙 하나는 우리가 직접 쟀습니다

DiffDock 재현성 주장 금지 규칙입니다. 호스팅 API에 시드 파라미터가 없어서, 같은 수용체와
리간드를 두 번 부르면 결과가 갈립니다.

```
1차:  [0.798, 0.751, 0.725]
2차:  [0.761, 0.693, 0.515]
```

남의 논문을 인용한 규칙이 아니고 우리 측정이 1차 근거입니다. 이 규칙 하나가 이 프로젝트의
고유 자산입니다.

## 안전 모델 둘을 더 얹었습니다

NVIDIA의 Safety Guard 8B v3와 Nemotron 3.5 Content Safety입니다. 뒤엣것에는 약물감시 전용
정책을 넣었는데, 공식 스킬 `nemotron-policy-generator`로 만들어 `custom_policy`로 넘깁니다.

막는 것 넷입니다.

- 개별 환자에 대한 치료 조언
- PRR을 인과로 단정하는 것
- 자발 보고로 발생률을 내는 것
- 재식별 시도

## 성능

일부러 넣은 틀린 주장 **31건 중 31건을 반려**하고 정상 문장 **6건 중 6건을 통과**시켰습니다.

다만 이 숫자를 읽을 때 주의할 것이 있습니다. 틀린 주장을 저희가 지어냈고, 규칙당 케이스가
1건씩 심긴 구조라 규칙별 구분력을 주장할 수 없습니다. 그리고 규칙 없이 일반 판정만으로도
13/16을 잡았으니 규칙 15종이 추가로 잡은 것은 3건뿐입니다.

그래서 **그 3건이 무엇인지가 중요합니다.** 단일 시드 재현성 주장, SMILES를 실행 입력이라
부르는 것, DiffDock에 시드가 없다는 사실인데, 셋 다 도구를 실제로 써 본 사람만 아는
것이고 일반 상식으로는 안 잡힙니다.

## 만들 때 순서

하루면 됩니다.

1. 주장마다 근거 ID를 붙이게 한다
2. **모델 없이** ID가 실재하는지 검사한다
3. **모델 없이** 숫자가 원본과 맞는지 검사한다
4. 남은 하나만 모델에 묻는다
5. 규칙 목록은 직접 짓지 말고 도구 문서에서 옮긴다

4번을 먼저 만들고 싶은 유혹이 있습니다. 모델에 다 물어보면 코드가 짧아지니까요.
그런데 그러면 검증기를 검증할 방법이 없어집니다. 앞의 둘을 기계로 해 두면 3단이 틀렸을 때
"3단만 틀렸다"고 말할 수 있습니다.
